# RAG (문서 기반 질의응답)

LangChain + OpenAI 임베딩 + Chroma(로컬 벡터 DB)로 만든 RAG 파이프라인입니다.
`data/`에 넣은 텍스트 문서를 검색 가능하게 저장하고, 질문하면 관련 부분을 찾아 GPT로 답을 생성합니다.
일반 텍스트 문서뿐 아니라 DART 공시 XML을 전용 파서로 구조화해서 넣을 수 있고, 검색은 벡터(의미) 검색과 BM25(키워드) 검색을 합친 하이브리드 방식을 씁니다.

## 설치

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -r requirements.txt

cp .env.example .env
# .env에 OPENAI_API_KEY를 채워 넣습니다
```

## 사용법

1. 문서를 `data/`에 넣습니다.
   - 일반 텍스트: `data/` 바로 아래에 `.txt` 파일로.
   - DART 공시 XML(사업보고서/반기보고서 등 `dart3.xsd` 스키마): `data/` 하위 아무 폴더(예: `data/dart_xml/`)에 `.xml`로 넣으면 재귀적으로 찾습니다. `dart_parser.py`가 SECTION 태그 구조를 따라가며 섹션 제목을 breadcrumb 형태(`I. 회사의 개요 > 1. 회사의 개요`)로 살려서 청크 metadata에 저장합니다.
2. 문서를 임베딩해서 저장:
   ```bash
   python ingest.py
   ```
   같은 파일을 다시 넣고 실행하면 기존 청크를 덮어씁니다 (upsert).
3. 질문하기:
   ```bash
   python query.py "이 보고서에서 매출에 영향을 준 지표는?"
   ```

## 구조

```
rag_core.py      LangChain 임베딩/LLM/텍스트 스플리터/Chroma 벡터스토어 공통 객체
dart_parser.py   DART 공시 XML 전용 파서: SECTION 트리를 breadcrumb 있는 Document 목록으로 변환
hybrid_search.py 벡터 검색 + BM25(키워드) 검색을 합치는 하이브리드 검색
ingest.py        data/*.txt, data/**/*.xml -> Document 변환 -> 청크 분할 -> Chroma 저장
query.py         질문 -> hybrid_search로 검색 -> LCEL 체인(prompt | llm)으로 답변 생성
data/            원본 문서 (git에는 커밋 안 됨)
```

`rag_core.py`가 만드는 공통 객체:
- `embeddings` — `OpenAIEmbeddings` (text-embedding-3-small)
- `llm` — `ChatOpenAI` (gpt-4o-mini)
- `text_splitter` — `RecursiveCharacterTextSplitter` (chunk_size=800, overlap=100)
- `vectorstore` — `Chroma` (embeddings와 연결된 로컬 벡터스토어)

### 청크 metadata

DART XML 청크에는 다음 metadata가 붙습니다 (`dart_parser.py`가 생성).

| 필드 | 내용 | 예시 |
|---|---|---|
| `source` | 원본 파일명 | `20210324000644.xml` |
| `chunk_index` | 그 파일 안에서 몇 번째 청크인지 | `90` |
| `company` | 회사명 (표기 변형이 있어 `hybrid_search.py`가 정규화해서 묶음) | `삼양이노켐 주식회사` |
| `doc_type` | 보고서 종류 | `반기보고서`, `사업보고서` 등 |
| `fiscal_period` | 그 파일이 다루는 회계기간 (표지의 PERIODFROM/PERIODTO 기반) | `2020.01.01~2020.12.31` |
| `ceo_name` | 대표이사 이름. 표지의 "대표이사 :" 라벨(공동대표는 콤마로 여러 명) 또는 감사보고서류의 재무제표 책임 확인 서명("회사명 대표이사 이름")에서 추출 | `조덕희`, `최낙현, 강호성` |
| `section` | 목차 breadcrumb | `VI. 이사회 등 회사의 기관에 관한 사항 > 1. 이사회에 관한 사항` |

### Contextual chunk header (검색 정확도의 핵심)

`company`/`ceo_name`/`fiscal_period`/`section`이 **metadata로만 있으면 검색(임베딩·BM25)에는 전혀 영향을 못 줍니다** — Chroma의 metadata는 필터링에만 쓰이고, 벡터/BM25는 오직 `page_content`만 보고 점수를 매기기 때문입니다. 그래서 예전엔 이런 일이 있었습니다.

- "삼양패키징 매출실적"을 물으면, 정작 매출실적 표 청크에는 "삼양패키징"이라는 글자가 아예 없어서 다른 회사·다른 청크에 밀림
- "삼양애니팜 대표이사가 누구야?"를 물으면, "대표이사"라는 단어를 여러 번 반복하는 회의 참석자 표가, 정작 이름이 딱 한 번 나오는 서명 문구보다 항상 유리해서 이름을 못 찾음

`ingest.py`의 `_context_header()`가 청크를 청크 분할(`text_splitter`) 이후, 임베딩하기 **직전**에 아래 형태의 헤더를 본문 맨 앞에 붙여서 이 문제를 근본적으로 해결합니다.

```
[(주)삼양패키징 | 대표이사 김재홍 | 사업연도 2020.01.01~2020.06.30 | II. 사업의 내용]
(원래 청크 본문...)
```

이러면 그 파일의 **모든 청크**가 회사명·대표이사 이름·사업연도를 텍스트로 갖게 되어, 검색이 어떤 청크를 집어오든 (심지어 엉뚱한 청크를 집어와도) 정답이 딸려 옵니다. 특히 `ceo_name`은 "이 회사 대표이사가 누구냐"는 질문이 반복적으로 실패해서 추가한 필드로, 랭킹을 굳이 정교하게 다듬는 대신 **답 자체를 모든 청크에 미리 심어두는** 방식으로 접근했습니다.

이 헤더 텍스트가 그대로 저장·임베딩되므로, `query.py`의 `format_docs()`는 인용 라벨을 `[source #chunk_index]`처럼 최소한으로만 붙입니다 (회사명 등은 이미 본문 첫 줄에 있어 중복 표시하지 않음).

`dart_parser.py`를 고쳐서 새 metadata 필드를 추가했거나 `ingest.py`의 헤더 형식을 바꿨다면, 기존에 저장된 청크의 `page_content` 자체를 다시 써야 하므로 metadata만 patch하는 걸로는 부족하고 **전체 재수집(재임베딩)**이 필요합니다.

## 검색 방식 (하이브리드: 의미 검색 + 키워드 검색)

`vectorstore.similarity_search()`만 쓰면 의미가 비슷한 문서를 찾아주긴 하지만, "회사명" 같은 고유명사가 질문에 있어도 그 회사 문서를 정확히 우선하지는 않습니다 (예: 여러 계열사 문서가 섞여 있으면 "대표이사"라는 단어가 자주 나오는 다른 회사 문서가 먼저 걸릴 수 있음). `hybrid_search.py`는 이를 보완합니다.

1. **회사명 자동 감지** — 저장된 청크의 `company` 메타데이터를 정규화(`(주)`/`주식회사`/공백 제거)해서 목록을 만들고, 질문에 그 회사명이 들어있으면 해당 회사의 청크로만 검색 범위를 좁힙니다.
2. **BM25(키워드) 검색** — 한글 조사(삼양패키징 vs 삼양패키징의) 때문에 단어 단위 토큰화가 잘 안 맞는 문제를 피하려고, 음절 2-gram으로 토큰화한 BM25를 씁니다.
3. **벡터(의미) 검색**과 **BM25 검색** 결과를 RRF(Reciprocal Rank Fusion)로 합쳐서 최종 top-k를 뽑습니다.

회사명이 질문에 없으면 1번 단계 없이 전체 문서에서 하이브리드 검색만 수행합니다. 회사 필터가 걸리면 검색어를 **회사명을 포함한 버전과 뺀 버전 둘 다** 만들어서(`_strip_company_mentions`) 벡터·BM25 각각에 두 번씩(총 4개 랭킹) 돌리고 전부 RRF로 합칩니다 — 회사명을 계속 언급하는 서술형 문단이 유리한 경우도 있고, 반대로 회사명을 빼야 그 안에서 진짜 찾는 키워드(예: "매출실적")가 잘 잡히는 경우도 있어서 둘 다 살려두는 게 더 안정적이었습니다. 앞서 설명한 **contextual chunk header** 덕분에 이제 모든 청크가 어차피 회사명을 갖고 있어서, 이 4-way 검색은 주로 회사명이 아닌 다른 키워드(매출실적, 감사참여자 등)의 매칭 정확도를 높이는 역할을 합니다.

### 회사명 없이 물으면 확인을 요청함

`query.py`의 `ask()`는 질문에 회사명이 없고(`_detect_company_filter`가 `None`), 실제로 검색된 top-k 청크가 **둘 이상의 회사**에 걸쳐 있으면 LLM을 호출하지 않고 바로 "어느 회사인지 질문에 포함해서 다시 물어봐 주세요"라는 안내와 함께 검색에 걸린 회사 목록을 보여줍니다. 이렇게 안 하면, 여러 계열사 자료가 섞인 채로 LLM에 넘어가서 실제로는 여러 회사 얘기가 섞여 있는데도 그중 하나만 골라 마치 유일한 정답인 것처럼 답해버리는 문제가 있었습니다 (예: 회사명 없이 "대표이사가 누구야?"라고 물으면 실제로는 삼양패키징과 삼양사 문서가 같이 검색됐는데도 삼양사 쪽 이름만 답했음). 검색된 청크가 우연히 한 회사로만 좁혀지는 일반적인 질문은 이 검사에 걸리지 않고 그대로 답변합니다.

## 알려진 한계

- **여러 연도의 표를 한 번에 종합해서 물으면 부정확할 수 있습니다.** 82개 DART 파일이 2020~2026년에 걸쳐 있어서, "전체 연도 감사참여자 인원수 다 알려줘"처럼 여러 해의 숫자 표를 한 답변에 종합해야 할 때 LLM이 가끔 연도-숫자 짝을 잘못 맞추는 경우가 있습니다. (대표이사처럼 "지금 누구냐"류 단일 사실 질문은 `ceo_name` contextual header 덕분에 이제 안정적입니다 — 이 한계는 여러 해의 수치를 한 답변 안에서 비교·나열해야 하는 경우에 해당합니다.) 특정 연도를 질문에 명시하면(`"삼양이노켐 2022년 감사참여자..."`) 정확도가 훨씬 높습니다.
- **표 안 당기/전기 열 혼동**: 재무제표류 표는 당기·전기 숫자가 한 청크 안에 같이 있어서, LLM이 둘을 바꿔 읽는 경우가 드물게 있습니다.

## 벡터 인덱스 저장 위치

기본값은 `~/.rag_project_chroma` (프로젝트 폴더 밖, 사용자 홈 디렉터리)입니다. `CHROMA_DIR` 환경변수로 바꿀 수 있습니다. 프로젝트 폴더 안(`.chroma/`)에 두지 않는 이유는, chromadb의 Rust 기반 HNSW 인덱스가 경로에 비ASCII 문자(한글 폴더명 등)가 섞이면 인덱스 파일을 제대로 못 만드는 버그가 있어서입니다 — 데이터는 sqlite에 정상 저장되지만 이후 조회 시 `Error loading hnsw index` 에러가 납니다. 프로젝트 경로 자체에 한글이 들어있는 한(`바탕 화면` 등) 이 문제를 피하려면 인덱스 디렉터리를 영문 경로로 분리해야 합니다.

## 노트북 사용 시 주의

노트북을 VSCode에 열어둔 상태에서 이 저장소의 `.py` 파일(특히 `hybrid_search.py`, `query.py`)이 바뀌면, 노트북 커널은 그 변경을 자동으로 반영하지 않습니다. `.py` 코드가 바뀐 뒤에는:
