# RAG (문서 기반 질의응답)

LangChain + OpenAI 임베딩 + Chroma(로컬 벡터 DB)로 만든 RAG 파이프라인입니다.
`data/`에 넣은 텍스트 문서를 검색 가능하게 저장하고, 질문하면 관련 부분을 찾아 GPT로 답을 생성합니다.
일반 텍스트 문서뿐 아니라 DART 공시 XML을 전용 파서로 구조화해서 넣을 수 있고, 검색은 벡터(의미) 검색과 BM25(키워드) 검색을 합친 하이브리드 방식을 씁니다.

## 설치

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -r requirements.txt

cp .env.example .env
# .env에 OPENAI_API_KEY를 채워 넣습니다
```

## 사용법

1. 문서를 `data/`에 넣습니다.
   - 일반 텍스트: `data/` 바로 아래에 `.txt` 파일로.
   - DART 공시 XML(사업보고서/반기보고서 등 `dart3.xsd` 스키마): `data/` 하위 아무 폴더(예: `data/dart_xml/`)에 `.xml`로 넣으면 재귀적으로 찾습니다. `dart_parser.py`가 SECTION 태그 구조를 따라가며 섹션 제목을 breadcrumb 형태(`I. 회사의 개요 > 1. 회사의 개요`)로 살려서 청크 metadata에 저장합니다.
2. 문서를 임베딩해서 저장:
   ```bash
   python ingest.py
   ```
   같은 파일을 다시 넣고 실행하면 기존 청크를 덮어씁니다 (upsert).
3. 질문하기:
   ```bash
   python query.py "이 보고서에서 매출에 영향을 준 지표는?"
   ```

## 구조

```
rag_core.py      LangChain 임베딩/LLM/텍스트 스플리터/Chroma 벡터스토어 공통 객체
dart_parser.py   DART 공시 XML 전용 파서: SECTION 트리를 breadcrumb 있는 Document 목록으로 변환 (표/문단 구분 포함)
hybrid_search.py 벡터 검색 + BM25(키워드) 검색을 합치는 하이브리드 검색
ingest.py        data/*.txt, data/**/*.xml -> Document 변환 -> 청크 분할 -> Chroma 저장
query.py         질문 -> hybrid_search로 검색 -> LCEL 체인(prompt | llm)으로 답변 생성
api.py           FastAPI 챗봇 서버 (POST /chat) — 배포 시 진입점
eval.py          정확도 회귀 테스트 스크립트
data/            원본 문서. DART XML(data/dart_xml/)은 공개 자료라 git에 커밋됨. data/*.txt는 제외됨
```

`rag_core.py`가 만드는 공통 객체:
- `embeddings` — `OpenAIEmbeddings` (text-embedding-3-small)
- `llm` — `ChatOpenAI` (gpt-4o-mini, `temperature=0`). 기본 temperature(사실상 1.0)로 두면, 컨텍스트에 정답이 그대로 있어도 같은 질문을 반복하면 어떨 땐 정답을 말하고 어떨 땐 "모른다"고 답하는 등 일관성이 없었다. 문서에서 사실을 뽑아 답하는 용도라 0으로 고정.
- `text_splitter` — `RecursiveCharacterTextSplitter` (chunk_size=800, overlap=100)
- `vectorstore` — `Chroma` (embeddings와 연결된 로컬 벡터스토어)

### 청크 metadata

DART XML 청크에는 다음 metadata가 붙습니다 (`dart_parser.py`가 생성).

| 필드 | 내용 | 예시 |
|---|---|---|
| `source` | 원본 파일명 | `20210324000644.xml` |
| `chunk_index` | 그 파일 안에서 몇 번째 청크인지 | `90` |
| `company` | 회사명 (표기 변형이 있어 `hybrid_search.py`가 정규화해서 묶음) | `삼양이노켐 주식회사` |
| `doc_type` | 보고서 종류 | `반기보고서`, `사업보고서` 등 |
| `fiscal_period` | 그 파일이 다루는 회계기간 (표지의 PERIODFROM/PERIODTO 기반) | `2020.01.01~2020.12.31` |
| `ceo_name` | 대표이사 이름. 표지의 "대표이사 :" 라벨(공동대표는 콤마로 여러 명) 또는 감사보고서류의 재무제표 책임 확인 서명("회사명 대표이사 이름")에서 추출 | `조덕희`, `최낙현, 강호성` |
| `affiliates` | 계열회사 명단. "계열회사 \| 법인등록번호"류 표에서 회사명 컬럼만 추출(ROWSPAN으로 행마다 컬럼 수가 달라도 "끝에서 두 번째 = 회사명, 마지막 = 법인등록번호"로 찾음). 분기보고서는 원본 자체에 상세표가 없어 빈 값일 수 있음 | `(주)삼양홀딩스, (주)삼양사, ...` |
| `section` | 목차 breadcrumb | `VI. 이사회 등 회사의 기관에 관한 사항 > 1. 이사회에 관한 사항` |
| `is_table` | 이 청크가 표에서 나왔는지 여부. 표는 문단과 잘리는 기준이 달라서(아래 "표 청크 분할 방식" 참고) | `True`/`False` |

### 표 청크 분할 방식

문단은 지금까지처럼 `RecursiveCharacterTextSplitter`(chunk_size=800)로 글자 수 기준으로 나누지만, **표는 별도로 처리**합니다 (`dart_parser.py`의 `_render_blocks`/`_merge_text_blocks`, `ingest.py`의 `_split_chunks`).

1. **표를 문단과 분리** — `dart_parser.py`가 XML의 `<TABLE>` 태그를 문단(`<P>`)과 별개 블록으로 떼어냅니다 (`TABLE-GROUP` 등에 중첩돼 있어도 재귀적으로 찾음). 그래야 800자 경계가 표 셀 중간을 가르는 걸 피할 수 있습니다.
2. **작은 표(`SMALL_TABLE_MERGE_LIMIT`, 200자 이하)는 다시 문단과 합침** — 표라고 무조건 떼어내면 "일자 | 주소 | 비고" 같은 몇 글자짜리 표까지 전부 독립 청크가 되어 청크 수가 크게 늘고, 그 표만 앞뒤 맥락 없이 뚝 떨어져서 검색되는 문제가 있었습니다.
3. **표 바로 앞의 짧은 캡션들(`CAPTION_MERGE_LIMIT`, 조각당 100자 이하, 합쳐서 `CAPTION_MERGE_TOTAL_LIMIT` 150자 이하)은 표에 붙임** — "(단위 : 명, 시간)"처럼 표를 소개하는 짧은 문구가 표와 분리되면, 실제 데이터 없이 캡션만 있는 청크가 생겨서 그게 오히려 진짜 데이터가 있는 표 청크보다 검색 랭킹에서 이겨버리는 문제가 있었습니다. 단위 캡션이 문단(`P`)이 아니라 테두리 없는 1칸짜리 `TABLE`로 렌더링된 경우도 있어서 "5. 매출에 관한 사항" / "가. 매출실적" / "(단위 :백만원)"처럼 짧은 조각이 표 바로 앞에 여러 개 연달아 쌓이기도 하는데, 끝에서부터 짧은 조각을 계속 모으다가 그 앞이 무관한 긴 문단(예: 설비투자현황 설명)이면 거기서 멈춥니다.
4. **남은(큰) 표는 크기로 나눔** — `TABLE_WHOLE_CHUNK_LIMIT`(1,500자) 이하면 통째로 한 청크, 넘으면 `_split_table_rows()`가 **행(row) 단위로만** 나눕니다(셀 중간 절대 안 자름). 표가 여러 조각으로 나뉘면 첫 번째 행(대개 헤더)을 각 조각 맨 위에 반복해서 붙여, 조각 하나만 봐도 어느 컬럼인지 알 수 있게 합니다. 단, 첫 행 자체가 비정상적으로 길면(그 자체가 긴 내용이지 헤더가 아닌 경우) 반복하지 않습니다.

행 경계는 문단 안에 원래 있던 줄바꿈과 구분하기 위해 내부적으로 특수 문자(`TABLE_ROW_SEP`)로 표시했다가, 최종 저장 직전에 일반 줄바꿈으로 되돌립니다 — 그렇지 않으면 셀 안에 여러 줄로 된 긴 문단(예: 정관 조항)이 행 경계로 오인되어 문장 중간에서 잘리는 문제가 있었습니다.

### `LIBRARY` 태그 데이터 유실 버그 (82개 파일 전체 영향)

`dart_parser.py`의 `SKIP_TAGS`에 예전엔 `LIBRARY`도 들어있었는데(내부 서식 참조인 `LIBRARYLIST`와 비슷하게 취급), 실제로는 **재무상태표/손익계산서/자본변동표/현금흐름표 같은 진짜 재무제표 TABLE-GROUP이 `LIBRARY` 태그 안에 들어있는 경우가 82개 파일 전부에서 발견됐습니다** (파일당 최대 40개). `LIBRARY`를 건너뛰면 이 표들이 통째로 사라져서, "유동자산 얼마야?" 같은 질문에 데이터가 있는데도 못 찾는 문제가 있었습니다. `LIBRARY`는 `SKIP_TAGS`에서 뺐고(표가 없는 `LIBRARY`는 안에 `FILENAME`/`INSERTION`만 있어서 그대로 둬도 노이즈가 안 생깁니다), 전체 재수집으로 반영했습니다 (청크 수 8,537 → 21,242).

### Contextual chunk header (검색 정확도의 핵심)

`company`/`ceo_name`/`fiscal_period`/`section`이 **metadata로만 있으면 검색(임베딩·BM25)에는 전혀 영향을 못 줍니다** — Chroma의 metadata는 필터링에만 쓰이고, 벡터/BM25는 오직 `page_content`만 보고 점수를 매기기 때문입니다. 그래서 예전엔 이런 일이 있었습니다.

- "삼양패키징 매출실적"을 물으면, 정작 매출실적 표 청크에는 "삼양패키징"이라는 글자가 아예 없어서 다른 회사·다른 청크에 밀림
- "삼양애니팜 대표이사가 누구야?"를 물으면, "대표이사"라는 단어를 여러 번 반복하는 회의 참석자 표가, 정작 이름이 딱 한 번 나오는 서명 문구보다 항상 유리해서 이름을 못 찾음

`ingest.py`의 `_context_header()`가 청크를 청크 분할(`text_splitter`) 이후, 임베딩하기 **직전**에 아래 형태의 헤더를 본문 맨 앞에 붙여서 이 문제를 근본적으로 해결합니다.

```
[(주)삼양패키징 | 대표이사 김재홍 | 사업연도 2020.01.01~2020.06.30 | II. 사업의 내용]
(원래 청크 본문...)
```

이러면 그 파일의 **모든 청크**가 회사명·대표이사 이름·사업연도를 텍스트로 갖게 되어, 검색이 어떤 청크를 집어오든 (심지어 엉뚱한 청크를 집어와도) 정답이 딸려 옵니다. 특히 `ceo_name`은 "이 회사 대표이사가 누구냐"는 질문이 반복적으로 실패해서 추가한 필드로, 랭킹을 굳이 정교하게 다듬는 대신 **답 자체를 모든 청크에 미리 심어두는** 방식으로 접근했습니다.

`affiliates`(계열회사 명단)는 값이 길고(회사 수십 개) 그 섹션에만 의미가 있어서 company/ceo_name과 달리 **모든 청크가 아니라 `section`에 "계열회사"가 들어간 청크에만** 헤더로 붙입니다 (`ingest.py`). "삼양패키징 계열회사 목록 알려줘" 같은 질문은 짧은 요약 문장("32개의 계열회사가 있습니다")이 실제 명단이 있는 상세표보다 항상 랭킹이 높게 나오는데, 두 청크 다 "계열회사" 섹션이라 헤더가 붙어있으므로 어느 쪽이 뽑히든 이제 이름 목록이 같이 나옵니다.

이 헤더 텍스트가 그대로 저장·임베딩되므로, `query.py`의 `format_docs()`는 인용 라벨을 `[source #chunk_index]`처럼 최소한으로만 붙입니다 (회사명 등은 이미 본문 첫 줄에 있어 중복 표시하지 않음).

`dart_parser.py`를 고쳐서 새 metadata 필드를 추가했거나 `ingest.py`의 헤더 형식을 바꿨다면, 기존에 저장된 청크의 `page_content` 자체를 다시 써야 하므로 metadata만 patch하는 걸로는 부족하고 **전체 재수집(재임베딩)**이 필요합니다.

## 검색 방식 (하이브리드: 의미 검색 + 키워드 검색)

`vectorstore.similarity_search()`만 쓰면 의미가 비슷한 문서를 찾아주긴 하지만, "회사명" 같은 고유명사가 질문에 있어도 그 회사 문서를 정확히 우선하지는 않습니다 (예: 여러 계열사 문서가 섞여 있으면 "대표이사"라는 단어가 자주 나오는 다른 회사 문서가 먼저 걸릴 수 있음). `hybrid_search.py`는 이를 보완합니다.

1. **회사명 자동 감지** — 저장된 청크의 `company` 메타데이터를 정규화(`(주)`/`주식회사`/공백 제거)해서 목록을 만들고, 질문에 그 회사명이 들어있으면 해당 회사의 청크로만 검색 범위를 좁힙니다.
2. **BM25(키워드) 검색** — 한글 조사(삼양패키징 vs 삼양패키징의) 때문에 단어 단위 토큰화가 잘 안 맞는 문제를 피하려고, 음절 2-gram으로 토큰화한 BM25를 씁니다.
3. **벡터(의미) 검색**과 **BM25 검색** 결과를 RRF(Reciprocal Rank Fusion)로 합쳐서 최종 top-k를 뽑습니다.

기본 top-k는 5가 아니라 **8**입니다(`hybrid_search()`/`ask()` 기본값). 정답 청크가 회사 필터까지 걸어도 정확히 top-5 안에 안 들고 6~8위 즈음에 있는 경우가 실제로 여러 번 있어서(예: 유동자산 질문에서 정답이 8위) 5보다 넉넉하게 잡았습니다.

회사명이 질문에 없으면 1번 단계 없이 전체 문서에서 하이브리드 검색만 수행합니다. 회사 필터가 걸리면 검색어를 **회사명을 포함한 버전과 뺀 버전 둘 다** 만들어서(`_strip_company_mentions`) 벡터·BM25 각각에 두 번씩(총 4개 랭킹) 돌리고 전부 RRF로 합칩니다 — 회사명을 계속 언급하는 서술형 문단이 유리한 경우도 있고, 반대로 회사명을 빼야 그 안에서 진짜 찾는 키워드(예: "매출실적")가 잘 잡히는 경우도 있어서 둘 다 살려두는 게 더 안정적이었습니다. 앞서 설명한 **contextual chunk header** 덕분에 이제 모든 청크가 어차피 회사명을 갖고 있어서, 이 4-way 검색은 주로 회사명이 아닌 다른 키워드(매출실적, 감사참여자 등)의 매칭 정확도를 높이는 역할을 합니다.

### 회사명 없이 물으면 확인을 요청함

`query.py`의 `ask()`는 질문에 회사명이 없고(`_detect_company_filter`가 `None`), 실제로 검색된 top-k 청크가 **둘 이상의 회사**에 걸쳐 있으면 LLM을 호출하지 않고 바로 "어느 회사인지 질문에 포함해서 다시 물어봐 주세요"라는 안내와 함께 검색에 걸린 회사 목록을 보여줍니다. 이렇게 안 하면, 여러 계열사 자료가 섞인 채로 LLM에 넘어가서 실제로는 여러 회사 얘기가 섞여 있는데도 그중 하나만 골라 마치 유일한 정답인 것처럼 답해버리는 문제가 있었습니다 (예: 회사명 없이 "대표이사가 누구야?"라고 물으면 실제로는 삼양패키징과 삼양사 문서가 같이 검색됐는데도 삼양사 쪽 이름만 답했음). 검색된 청크가 우연히 한 회사로만 좁혀지는 일반적인 질문은 이 검사에 걸리지 않고 그대로 답변합니다.

### 근거 없을 때의 응답 문구

`ask()`가 문서 근거를 못 찾았을 때 사용자에게 보여주는 문구는 "관련 내용을 찾지 못했습니다. 질문을 바꿔서 다시 문의해 주세요."입니다. 이 문구를 **프롬프트에 직접 넣어서 LLM이 그대로 말하게 시키는 방식은 실패**했습니다 — "모른다고 답하세요"보다 문구가 길고 단정적이다 보니 모델이 훨씬 쉽게 거부 판정을 내려서, 원래 정상 답변하던 "삼양이노켐 감사참여자 알려줘"(표에 인원수/시간만 있고 사람 이름은 없는 경우)까지 근거가 있는데도 거부하는 회귀가 생겼습니다.

그래서 **판단(거부할지 말지)과 표시 문구를 분리**했습니다. `query.py`의 프롬프트는 검증된 원래 지시("모른다고 답하세요")를 그대로 쓰고, `ask()`가 LLM 응답에 `모른다`/`모릅니다`가 들어있는지 코드에서 확인해서, 있으면 최종적으로 `"관련 내용을 찾지 못했습니다. 질문을 바꿔서 다시 문의해 주세요."`로 치환해서 반환합니다. 이러면 모델의 의사결정 경계는 이전과 동일하게 유지하면서 사용자에게 보이는 문구만 원하는 대로 바꿀 수 있습니다. (`eval.py`의 `no_data`/`factual` 판정 마커도 `찾지 못했습니다`로 맞춰 갱신했습니다.)

## 로그

- **`ingest.py`** — 문서를 넣을 때 각 청크의 인덱스/유형(문단·표)/길이/섹션/미리보기를 한 줄씩 콘솔에 출력합니다.
- **`hybrid_search.py`** — `hybrid_search()`를 호출하면(직접 호출이든 `query.py`/노트북을 통해서든) 감지된 회사 필터와 최종 top-k 청크의 순위·RRF 점수·출처·섹션을 출력합니다.

## 정확도 평가 (`eval.py`)

질문을 하나씩 손으로 던져보며 확인하던 걸 자동화한 회귀 테스트 스크립트입니다.

```bash
python eval.py
```

### 측정 지표

- **검색(Retrieval) 지표** — 질문에 해당하는 회사의 청크가 `hybrid_search()` 상위 k(=8)개 안에 들어왔는지/몇 위인지를 본다.
  - **Hit Rate@8**: 정답 회사의 청크가 top-8 안에 있는 질문의 비율
  - **MRR**(Mean Reciprocal Rank): 그 청크가 몇 위였는지의 역수 평균 (1위=1.0, 8위=0.125)
- **답변(Answer) 지표** — `query.ask()`의 최종 답변에 정답이 들어있는지를 질문 유형별로 다르게 검증한다.
  - `ceo`/`affiliates` 유형은 지금 vectorstore에 저장된 `ceo_name`/`affiliates` metadata 값을 그 자리에서 읽어와 정답 후보로 삼는다 — 하드코딩하지 않으므로 재수집으로 데이터가 바뀌어도 eval 코드를 고칠 필요가 없다.
  - `factual` 유형(매출실적/유동자산 등 구조화 metadata가 없는 숫자 질문)은 "찾지 못했습니다" 같은 명시적 거부 문구가 없으면 통과로 보는 **약한 검증**만 한다. 즉 숫자 자체가 맞는지는 자동으로 확인하지 못하며, 결과 표에도 이 한계를 그대로 표시한다.
  - `no_data` 유형은 반대로 corpus에 근거 문서가 아예 없는 질문(예: 감사보고서만 있는 회사에 임원현황을 물음)을 넣어, LLM이 지어내지 않고 정직하게 "찾지 못했습니다"류로 답하는지 보는 **환각 방지 회귀 테스트**다.
  - `disambiguation` 유형은 회사명 없는 질문에 확인 요청 문구가 나오는지를 본다.

### 현재 결과

`EVAL_CASES` 10문항 기준: **Hit Rate@8 9/9(100%), MRR 1.000, 답변 정확도 10/10(100%)**.

### eval 스크립트 자체에서 배운 것

처음 만들었을 때 "삼양데이타시스템 임원현황 알려줘"가 실패로 나왔는데, 원인을 파고드니 RAG 버그가 아니라 두 가지 다른 문제였습니다.

- **테스트 케이스 선정 오류**: 삼양데이타시스템은 corpus에 감사보고서만 있고 임원현황이 실리는 사업/반기/분기보고서가 아예 없어서, "모른다"가 정직한 정답이었습니다. → 이 케이스는 `no_data` 유형으로 남기고, 실제 데이터가 있는 삼양사로 별도 `factual` 케이스를 추가했습니다.
- **약한 검증 마커가 너무 넓었음**: "모른다류" 판정에 `없습니다`를 포함시켰더니, "이 외의 임원 현황 정보는... 해당 사항이 없습니다"처럼 그냥 "더 없다"는 뜻으로 쓰인 정상 답변까지 오답 처리됐습니다. → 마커를 `모른다`/`모릅니다`/`알 수 없`으로 좁혀서 해결.

즉 eval 스크립트의 "정답 판정 로직"도 코드인 이상 버그가 날 수 있으므로, [O]/[X] 판정을 그대로 믿기보다는 실패로 뜬 케이스의 실제 답변 내용을 한 번은 직접 읽어보는 게 안전합니다.

## 알려진 한계

- **여러 연도의 표를 한 번에 종합해서 물으면 부정확할 수 있습니다.** 82개 DART 파일이 2020~2026년에 걸쳐 있어서, "전체 연도 감사참여자 인원수 다 알려줘"처럼 여러 해의 숫자 표를 한 답변에 종합해야 할 때 LLM이 가끔 연도-숫자 짝을 잘못 맞추는 경우가 있습니다. (대표이사처럼 "지금 누구냐"류 단일 사실 질문은 `ceo_name` contextual header 덕분에 이제 안정적입니다 — 이 한계는 여러 해의 수치를 한 답변 안에서 비교·나열해야 하는 경우에 해당합니다.) 특정 연도를 질문에 명시하면(`"삼양이노켐 2022년 감사참여자..."`) 정확도가 훨씬 높습니다.
- **표 안 당기/전기 열 혼동**: 재무제표류 표는 당기·전기 숫자가 한 청크 안에 같이 있어서, LLM이 둘을 바꿔 읽는 경우가 드물게 있습니다.

## 벡터 인덱스 저장 위치

기본값은 `~/.rag_project_chroma` (프로젝트 폴더 밖, 사용자 홈 디렉터리)입니다. `CHROMA_DIR` 환경변수로 바꿀 수 있습니다. 프로젝트 폴더 안(`.chroma/`)에 두지 않는 이유는, chromadb의 Rust 기반 HNSW 인덱스가 경로에 비ASCII 문자(한글 폴더명 등)가 섞이면 인덱스 파일을 제대로 못 만드는 버그가 있어서입니다 — 데이터는 sqlite에 정상 저장되지만 이후 조회 시 `Error loading hnsw index` 에러가 납니다. 프로젝트 경로 자체에 한글이 들어있는 한(`바탕 화면` 등) 이 문제를 피하려면 인덱스 디렉터리를 영문 경로로 분리해야 합니다.

## 배포 (FastAPI + 클라우드 PaaS)

`api.py`가 챗봇 서버 진입점입니다.

```bash
uvicorn api:app --host 0.0.0.0 --port 8001
```

기존에는 `python ingest.py`를 터미널에서 수동으로 실행해야 데이터가 채워졌는데, 배포 환경에서는 터미널 접근 없이도 최초 배포 시 자동으로 채워지도록 `api.py`의 FastAPI `lifespan` 훅에서 처리합니다.

### Render 무료 플랜 배포 실패 문제와 해결 (`chroma_data/` 사전 빌드 커밋)

Render 무료 플랜은 영구 디스크(Persistent Disk)를 지원하지 않아 컨테이너 파일시스템이 **배포마다** 초기화됩니다. `_ingest_if_empty()`가 `lifespan` 시작 훅에서 동기적으로 실행되는데, 벡터스토어가 매번 비어 있으니 매 배포마다 82개 DART XML 전체를 OpenAI로 재임베딩하게 되고, 이 작업이 Render의 포트 감지 제한 시간보다 오래 걸려 `No open ports detected` → `Exited with status 3`로 배포가 실패했습니다 (2026-07-30 확인).

해결책: 로컬에서 미리 만들어둔 Chroma 벡터스토어(`~/.rag_project_chroma`)를 **Git LFS**로 레포의 `chroma_data/`에 커밋해뒀습니다. `chroma.sqlite3`(약 210MB)와 HNSW 인덱스 `.bin` 파일들은 GitHub의 100MB 단일 파일 제한을 넘기 때문에 일반 git이 아니라 LFS로 추적합니다(`.gitattributes` 참고). 이러면 Render가 git clone할 때 이미 채워진 벡터스토어가 함께 딸려오므로, 서버 기동 시 `count() > 0`이라 자동 수집을 완전히 건너뛰고 즉시 포트를 엽니다.

**배포 시 필요한 것 두 가지**

1. **`CHROMA_DIR`을 `chroma_data/`로 지정** — Render 환경변수에 `CHROMA_DIR=chroma_data`(레포 루트 기준 상대경로, 앱이 레포 루트에서 기동되므로)를 설정해야 커밋된 사전 빌드 데이터를 읽습니다. 설정 안 하면 기본값(`~/.rag_project_chroma`)을 보게 되어 다시 빈 스토어로 시작합니다.
2. **DART XML 원본이 배포 환경에 존재** — `data/dart_xml/`은 DART 공시(공개 자료)라 `.gitignore`에서 제외해 git에 커밋해뒀습니다(용량 약 118MB, 개별 파일 최대 7MB로 GitHub 제한 안에 들어옴). `data/*.txt`(일반 텍스트 문서)는 여전히 커밋하지 않습니다. (자동 수집을 안 타는 한 이 데이터는 실제로는 쓰이지 않지만, 벡터스토어를 지우고 처음부터 다시 만들어야 할 때를 대비해 유지합니다.)

**주의(Git LFS 대역폭)**: GitHub 무료 티어는 LFS 저장/대역폭이 월 1GB입니다. `chroma_data/`가 약 330MB라 Render가 배포마다 이걸 pull하면 한 달에 대략 3번 배포하면 무료 대역폭을 다 씁니다. 배포를 자주 한다면 LFS 데이터 팩 구매 또는 유료 플랜(영구 디스크)로 전환을 고려하세요. 또한 Render가 clone 시 LFS 스무징을 실제로 수행하는지(즉 `chroma_data/chroma.sqlite3`가 진짜 210MB 바이너리로 받아지는지, 아니면 LFS 포인터 텍스트 파일 그대로인지)는 첫 배포 로그에서 반드시 확인해야 합니다.

**문서가 바뀌면**: `data/`에 파일을 추가/교체한 뒤 로컬에서 `python ingest.py`(또는 재수집이 필요하면 `chroma_data/`를 지우고) 다시 실행하고, 그 결과를 `chroma_data/`에 복사해 다시 커밋합니다.

### 자동 수집 동작 방식 (`api.py`의 `_ingest_if_empty()`)

서버가 시작할 때 `vectorstore._collection.count()`로 저장된 청크 수만 가볍게 확인합니다.
- **0개(최초 배포, 볼륨이 비어있음)** → `ingest.py`의 `main()`을 자동으로 실행해 `data/`의 모든 문서를 수집합니다.
- **1개 이상(이미 이전 배포에서 수집됨)** → 그대로 건너뜁니다. 재배포마다 매번 재수집하면 시간도 오래 걸리고(현재 82개 파일 기준 레이트리밋 페이싱 포함 상당한 시간) OpenAI 임베딩 비용도 매번 나갑니다.

**주의**: 이 자동 수집은 `lifespan` 시작 훅 안에서 동기적으로 실행되므로, **최초 배포에서는 수집이 끝나기 전까지 서버가 요청(헬스체크 포함)에 응답하지 않습니다.** 플랫폼의 헬스체크 유예 시간(health check grace period)이 짧으면 첫 배포가 실패로 오인될 수 있으니, 배포 플랫폼 설정에서 헬스체크 타임아웃을 넉넉히(최소 10분 이상 권장) 잡아야 합니다. 이후 재배포부터는 count() 확인만 하고 바로 응답하므로 빠릅니다.

문서를 추가/교체해서 재수집이 필요하면, 볼륨의 기존 데이터를 지우고 재배포하거나, 터미널 접근이 가능한 환경이면 그냥 `python ingest.py`를 다시 실행하면 됩니다 (upsert라 안전합니다).

## 노트북 사용 시 주의

노트북을 VSCode에 열어둔 상태에서 이 저장소의 `.py` 파일(특히 `hybrid_search.py`, `query.py`)이 바뀌면, 노트북 커널은 그 변경을 자동으로 반영하지 않습니다. `.py` 코드가 바뀐 뒤에는:
- 코드만 바뀐 경우 → 커널 **재시작(Restart)** 후 다시 실행
- `explore_data.ipynb` 자체가 외부에서 바뀐 경우 → 노트북 탭을 **저장하지 않고 닫았다가** 다시 열어야 함 (열어둔 채로 셀을 실행하면 에디터가 들고 있던 이전 버전이 다시 저장되며 덮어씁니다)

## 개발 히스토리 (문제 → 원인 → 해결)

이 프로젝트가 지금 형태로 오기까지 겪은 문제들을 시간 순으로 정리합니다. 각 항목의 자세한 메커니즘은 위 해당 섹션에 있습니다.

### 1. 초기 구현 → LangChain 마이그레이션
처음엔 `openai` SDK와 `chromadb`를 직접 호출하는 최소 구현(임베딩 함수 하나, Chroma 클라이언트 하나)이었습니다. LangChain으로 옮기면서 `OpenAIEmbeddings`/`ChatOpenAI`/`Chroma`/`RecursiveCharacterTextSplitter`로 교체해 부품을 갈아끼우기 쉬운 구조로 바꿨습니다.

### 2. DART 공시 XML 지원 추가
일반 텍스트 문서만 다루다가, DART 공시 XML(`dart3.xsd` 스키마)을 구조화해서 넣는 `dart_parser.py`를 새로 만들었습니다. XML 자체가 표준을 안 지키는 부분이 있어서 전처리가 필요했습니다.
- **문제**: 비표준 `&cr;` 개행 엔티티, 이스케이프 안 된 `<`/`>`(예: 본문에 `<당기말>`처럼 꺾쇠를 문자 그대로 씀), 이스케이프 안 된 `&` 때문에 일반 XML 파서가 못 읽음.
- **해결**: 파싱 전에 `&cr;`→줄바꿈 치환, 진짜 태그가 아닌 `<`/`>`/`&`만 골라서 이스케이프하는 전처리 추가.

### 3. chromadb 벡터 인덱스가 한글 경로에서 깨짐
82개 파일을 처음 다 넣고 나서, 새 프로세스로 다시 열면 `Error loading hnsw index` 에러가 났습니다.
- **원인**: 프로젝트 경로에 한글 폴더명(`바탕 화면`)이 있으면 chromadb의 Rust 기반 HNSW 인덱스가 인덱스 파일을 제대로 못 만드는 버그. (OneDrive 자체는 원인이 아님 — ASCII 경로면 OneDrive 안이어도 정상 동작하는 것까지 확인.)
- **해결**: 벡터 인덱스 저장 위치를 프로젝트 밖 사용자 홈 디렉터리(`~/.rag_project_chroma`)로 이전 (`CHROMA_DIR` 환경변수로 조정 가능).

### 4. 임베딩 API 레이트리밋
82개 파일을 한 번에 넣다가 `text-embedding-3-small`의 분당 토큰 한도(TPM)에 걸려 중간에 멈췄습니다.
- **해결**: 파일 여러 개 처리할 때마다 몇 초씩 쉬어가는 방식으로 페이싱.

### 5. 검색 정확도 문제 연쇄 (가장 오래 걸린 부분)
질문 하나씩 실제로 테스트하면서 아래 문제들을 순서대로 발견하고 고쳤습니다.

1. **벡터 검색만으로는 회사 구분이 안 됨** — 여러 계열사 문서가 섞여 있으면, 질문에 회사명이 있어도 "대표이사"처럼 자주 나오는 단어가 있는 다른 회사 문서가 먼저 걸림. → BM25(키워드) 검색을 추가하고 RRF로 벡터 검색과 합치는 `hybrid_search.py` 도입.
2. **회사명을 검색어에 남기면 vs 빼면 서로 다른 실패** — 회사명을 그대로 두면 회사명을 반복 언급하는 서술형 문단이 유리해지고(표 데이터가 밀림), 회사명을 빼면 남는 검색어가 너무 짧고 흔해서(예: "대표이사") 반대로 실패하는 경우가 있었음. → 회사명 포함/제외 버전을 **둘 다** 검색해서 합치는 방식으로 정착.
3. **회사/대표이사/연도가 metadata에만 있어서 검색 랭킹에 영향을 못 줌** — Chroma metadata는 필터링에만 쓰이고 임베딩·BM25 점수는 `page_content`만 본다는 걸 뒤늦게 파악. "삼양애니팜 대표이사가 누구야?" 같은 질문이 반복적으로 실패한 근본 원인이었음. → 청크 본문 맨 앞에 회사명/대표이사/사업연도/섹션을 텍스트로 박아넣는 **contextual chunk header** 도입.
4. **계열회사 목록 질문 실패** — "32개의 계열회사가 있습니다" 같은 짧은 요약 문장이, 실제 회사명이 나열된 상세표보다 항상 검색 랭킹이 높음. → `affiliates` 필드를 별도로 뽑아 "계열회사" 섹션 청크에만 헤더로 추가.
5. **매출실적/감사참여자 질문에서 캡션만 있는 청크가 이김** — "(단위 : 백만원)" 같은 캡션이 표와 분리되면서 캡션만 있고 숫자는 없는 청크가 생겼고, 이게 실제 데이터가 있는 표보다 랭킹이 높았음. → 표 바로 앞 짧은 캡션(들)을 표에 붙이는 로직 추가 (처음엔 마지막 조각 하나만 봤다가, 짧은 조각이 여러 개 연달아 나오는 경우를 놓쳐서 "끝에서부터 짧은 조각을 계속 모으는" 방식으로 개선).
6. **같은 질문을 반복하면 답이 오락가락함** — 컨텍스트에 정답이 그대로 있어도 어떨 땐 맞히고 어떨 땐 "모른다"고 답함. → `ChatOpenAI`의 `temperature`를 명시적으로 설정 안 해서 기본값(사실상 1.0)을 쓰고 있었던 게 원인. `temperature=0`으로 고정.
7. **"유동자산 얼마야?" 질문 실패, 원인은 데이터 유실** — `dart_parser.py`의 `SKIP_TAGS`에 `LIBRARY` 태그가 있었는데, 재무상태표·손익계산서 등 진짜 재무제표가 `LIBRARY` 태그 안에 들어있는 경우가 **82개 파일 전부**에서 발견됨(파일당 최대 40개). → `LIBRARY`를 `SKIP_TAGS`에서 제거, 전체 재수집.
8. **정답이 top-5 밖(6~8위)에 있어서 여전히 실패** — 위 유실 버그를 고쳐도 정답 청크가 벡터 검색에서 1위인데 BM25에서 밀려 최종 RRF 순위가 top-5 밖으로 나가는 경우가 있었음. → 기본 top-k를 5 → 8로 상향.
9. **회사명 없이 물으면 엉뚱하게 확정적으로 답함** — 여러 회사 문서가 섞여 검색됐는데도 그중 하나만 골라 마치 유일한 정답인 것처럼 답함. → 회사명이 질문에 없고 검색 결과가 2개 이상 회사에 걸치면, LLM 호출 없이 회사명을 명시해 달라고 되묻도록 변경.

### 6. 표 청크 분할 개선 (진행하며 균형점을 찾음)
표가 문단과 합쳐진 채로 800자 기준으로 잘리면서 셀 중간이 잘리는 문제가 있어 표/문단을 분리했는데, 그러자 이번엔 부작용이 나타났습니다.
- **1차 시도**: 표는 무조건 별도 청크 → 아주 작은 표("일자|주소|비고" 몇 글자)까지 다 떨어져 나와 청크 수가 7,763 → 18,272개로 폭증.
- **2차 시도**: 작은 표(200자 이하)는 다시 문단과 병합 → 청크 수 10,042개로 정상화. 그런데 표 바로 앞 캡션이 표와 분리되는 부작용 발견(위 5-5번).
- **3차**: 캡션 병합 로직 추가/개선 → 8,537개로 재조정.
- **4차**: `LIBRARY` 버그를 고치며 그동안 숨어있던 진짜 재무제표 데이터가 복구되어 21,242개로 증가 (노이즈가 아니라 실제 데이터 회복).

### 7. 노트북(explore_data.ipynb) 관련 반복 이슈
- VSCode에 노트북을 열어둔 채로 `.py` 파일이나 노트북 파일 자체를 코드로 수정하면, 에디터가 들고 있던 이전 버전이 나중에 다시 저장되며 수정 내용을 덮어쓰는 일이 여러 번 있었음 → 파일을 고친 뒤에는 노트북 탭을 저장하지 않고 닫았다가 다시 열어야 함.
- 커널이 떠 있는 동안 `.py` 코드를 고쳐도 이미 임포트된 모듈은 그대로라 반영이 안 됨 → 커널 재시작 필요.
- 회사명 필터/BM25 인덱스가 프로세스당 캐시되기 때문에, 재수집 직후 같은 프로세스(노트북 등)에서 바로 검색하면 새 데이터가 안 잡힐 수 있음 → `ingest.py` 실행이 끝나면 `hybrid_search.reset_cache()`를 호출해 캐시를 비움.
